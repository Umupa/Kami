# 决策记录

每条写清楚决定、理由和放弃的方案，只记当前有效的决定。决定被推翻时直接改原条目并更新日期，不保留过时版本；编号不复用。

## D1 独立实现 Kami（2026-10-19）

**决定**：使用 Go 和 MyGo 实现桌面 AI 工具箱，需求与结构由本项目文档定义。

**理由**：Markdown 流式渲染、多轮对话、提示词模式和模型配置需要统一设计；独立实现便于明确模块边界，并让业务核心可以无窗口测试。

**放弃**：围绕单一翻译场景构建专用结果视图；为不同模式维护独立处理管线。

## D2 用 MyGo 原生 UI，不用 SwiftUI，也不用 WebView（2026-10-18）

**决定**：界面用 MyGo 的 `ui` 包（Go 写、GPU 自绘、Core Text 排字），不用它的 WebView 模式。

**理由**：
- `ui/markdown` 自带为 LLM 流式回复设计的 GFM 渲染（增量解析、半截语法、匀速出字、淡入），覆盖结果呈现的需求。
- 原生 UI 窗口打开即有内容、内存小，满足面板「按下即出现」。
- MyGo 已覆盖面板窗口、全局快捷键、菜单栏、透明窗口、文件监听、打包签名和更新。

**代价**：MyGo 很新，锁定精确版本，升级单独评估（architecture.md §一）。

**放弃**：SwiftUI + AppKit（成熟，但与用 Go 的初衷不符）；MyGo WebView 模式（Markdown 生态更全，但唤起慢、内存大）。

## D3 系统 API 用 purego 直连，不用 cgo（2026-10-18）

**决定**：辅助功能、CGEvent（含事件监听）、NSPasteboard、Vision、ScreenCaptureKit 都通过 purego / purego/objc 调用，封装在 `internal/macos`。

**理由**：保持「纯 Go、无 cgo」，构建只要 Go；MyGo 自己就是这样调系统的。

**退路**：Objective-C block 或回调太难处理时，用 MyGo 的 helper executable 附带一个小的 Swift 工具，通过标准输入输出通信。

## D4 不保存会话（2026-10-18）

**决定**：会话、原文、结果只在内存里，退出即消失；日志不含文字。

**理由**：减少文字内容的持久化；不需要保存提示词和对话历史。笔记是用户主动保存的内容，不受这条约束（D18）。

## D5 模式就是提示词预设（2026-10-19）

**决定**：模式 = 名字 × 提示词 × 输入语义 × 输出格式（architecture.md §四）；所有模式用同一个模型（D22），走同一条管线，没有按模式分支的代码；内置翻译、润色、问答三个预设（D15）。

**理由**：这些场景的差别只在提示词；场景再多也只是多一段提示词。

**例外**：Operator 和笔记在模式条上占位置，但它们是面板的特殊状态，不是提示词预设，不走模式管线（D13、D18）。

**放弃**：给模式加语言规则、预处理、结果去处等更多维度；「Agent 转译」模式（边界说不清）。

## D6 每个结果都可以追问（2026-10-18）

**决定**：多轮对话不是单独的窗口，而是任何结果之后的延伸；问答模式以对话开始。Material 模式的合约规定：第一条用户消息是材料，之后的用户消息是追问指令。

**理由**：多数时候用户要的是「把这段变成那样」，对话是对结果的调整；同时保住防注入。

## D7 面板 ⌥空格，带入选区双击 ⌥，截图 ⌥S（2026-10-20）

**决定**：面板 `option+space`，带入选区 `double-option`，截图 `option+s`。三个入口都可以是组合键或双击修饰键。开发与日常使用同一套。

**理由**：macOS 会把同一个热键同时发给所有注册了它的应用，双击修饰键不占任何组合键，所以给最常用的带入选区；第二次松开时触发，模拟 ⌘C 时没有修饰键按着。代价是输入监控权限。面板保留组合键，不依赖权限也能打开。⌥S 与 ⌥空格同属 ⌥ 系列，好记，只占掉不常用的 ß。

**放弃**：⌥A（占掉 å，和 ⌥S 相邻容易按错）；开发期改用 ⌃⌥ 组合（日常与开发用同一套，才能尽早发现冲突）。

## D8 自签名证书保证授权不丢（2026-10-18）

**决定**：用本机自签名的代码签名身份 `Kami Dev`。`scripts/build.sh`、`scripts/dev.sh` 都用它签名，缺少时由 `scripts/dev-cert.sh` 创建，不自动降级为临时签名；临时产物需显式传入 `--ad-hoc`。构建后检查签名，仍是临时签名就报错。

**理由**：辅助功能、输入监控和屏幕录制的授权绑定应用标识与签名身份；临时签名每次构建都会变，授权随之失效，而系统设置里旧条目的开关仍显示为开启，看起来像已经授权。没有 Developer ID（D27）。

**影响**：`mygo dev` 的应用是另一个应用（`Kami Dev`、`dev.umupa.kami.dev`），授权和数据目录与正式构建分开。授权记录错乱时用 `scripts/reset-permissions.sh` 清除，再按提示重新授权。

## D9 不依赖大模型 SDK（2026-10-18）

**决定**：`net/http` + 自写 SSE 解析器支持三种格式。

**理由**：只用到流式补全一个接口；三家 SDK 的依赖和行为差异不值得；服务地址、认证与请求参数由统一的配置字段描述。

## D10 只留三个入口，不改写其他应用（2026-10-20）

**决定**：入口只有 ⌥空格（打开面板）、双击 ⌥（带入选区）、⌥S（截图）。不做原处改进和原处翻译，也不做听写。

**理由**：直接修改其他应用的文字依赖辅助功能细节，还需要写回选区并核对原文没变；这不是高频用法，润色在面板里完成再复制即可。

**放弃**：直接改写其他应用选区的入口（⌥F、⌥D / ⌥⇧D）。

## D11 终端清洗交给模型，截图段落在本机恢复（2026-10-21）

**决定**：终端控制符、框线与原文语言判断交给模型。截图例外：按识别框在本机恢复同行、自然折行与段落，保留主动断行与列表；截图固定执行翻译，不跟随默认模式，也不把识别出的文字解释成面板命令。

**理由**：识别框带着位置，本机就能恢复阅读顺序，进入原文栏的内容应当已经可读；终端输入来源复杂，没有这样的信息，由模型清洗更可靠。

**代价**：段落恢复要靠用例维护；真实桌面效果只能手动验收。

## D12 配置文件就是 agent 接口（2026-10-22）

**决定**：全部设置在带 JSON Schema 的 `config.json` 里，API Key 也在里面（`model.apiKey`），应用热加载；命令行只有 `check`；配置交给 Coding Agent。

**理由**：agent 可以直接读写配置文件，不需要 `config set/show/schema` 这一套命令；`check` 负责校验并实际请求模型服务，确认配置可用。

**Key 为什么不放钥匙串**：钥匙串条目的分区列表在没有 Team ID 时记录的是二进制的 cdhash，自签名应用每重新构建一次都要重新授权；而且要多一个 `key` 子命令。放进配置文件最简单，agent 一次就能配好。

**代价**：Key 以明文存在 `config.json`（权限 0600）；agent 读写这个文件时，Key 会进入它的上下文，配置提示词要求 agent 不复述 Key。备份工具会备份这个文件。

**放弃**：覆盖全部设置的命令行接口；MCP 服务（要常驻本地服务，超出需要）；登录钥匙串；单独的 keys.json（多一个文件和一条规则）。

## D13 不做设置窗口，通过 Operator 设置（2026-10-18）

**决定**：不做设置窗口。大多数设置从面板里的 `/operator` 用一句话问或改，由模型理解，应用校验后直接写入 `config.json`，可撤销。主题另有本地 `/theme` 选择器，Dock 显示开关放在菜单栏菜单里，两者都不依赖模型；模型服务交给 Coding Agent。参考 monocode 的 `/operator`：命令变色、模式药丸、发送时的星星。

**理由**：这个应用的一切都在一个对话框里发生，设置也应该是对话。配好模型之后，应用能用这个模型配置自己，不用再去找 Coding Agent。

**放弃**：设置窗口；在对话流里插入卡片、按钮这类新组件（不够原生）；改动先确认再生效（多一步，撤销已足够）；在 Operator 里输入 API Key（还需要 endpoint 等，交给 Agent 更简单）。

## D14 Omarchy 的外观，monocode 的对话（2026-10-22）

**决定**：配色、字体、形状来自 Omarchy：默认 flexoki-light（深浅两套，可换），一种等宽字体贯穿全程，小圆角、1px 细边框、无阴影，键盘优先。对话的度量来自 monocode：正文 13.5pt、行高 1.65，逐词 320ms 淡入，等待时的呼吸提示，追问以提示符 `❯` 开头，元信息在最新一轮常显、其余悬停时显示，输入 `/` 列出命令。所有数值在 `internal/design`；截图层另有自己的外观（D19）。

**理由**：界面需要同时容纳对话、代码和配置；等宽字体与统一配色能让这些内容保持一致。

**放弃**：以纸面配色和比例字体作为默认外观；气泡式用户消息（与扁平风格不合）。

## D15 内置三个模式：翻译、润色、问答（2026-10-24）

**决定**：内置模式只有翻译、润色、问答。润色把文字改得通顺准确；内容杂乱时顺带整理成标题、列表和表格。配置里的 `organize` 视为 `improve`；写着 `prompt` 而没有自己提示词的条目忽略，不报错。

**理由**：改进与整理都是「把这段文字改好」，差别只在原文是否杂乱，由模型判断即可。提示词梳理用得少，需要时可以用 Operator 加一个自定义模式。模式越少，Tab 切换和斜杠菜单越短。

**放弃**：改进与整理分成两个模式；保留提示词梳理；把配置里的 `prompt` 当作配置错误（已移除的主题也是改用默认，不报错）。

## D16 毛玻璃、内置 Caskaydia、可固定（2026-10-19）

**决定**：面板背景默认毛玻璃，可改实色；字体只有随应用内置的 CaskaydiaCove Nerd Font，界面、正文与代码统一使用，字号可调，加载失败明确报错；缺少的中文、emoji 字形由 macOS 补齐；截图提示胶囊用系统界面字体。面板可固定。

**理由**：实色面板质感不足；内置字体保证换一台 Mac 也是同一种字体，不因本机未安装而悄悄换成别的。

**放弃**：多个字体预设和静默替代字体；主题壁纸作背景（干扰阅读）。

## D17 名称为 Kami（2026-10-23）

**决定**：产品名只有 `Kami`，中文里也这样称呼。项目与应用一致：GitHub 仓库 `Umupa/Kami`，Go 模块 `github.com/Umupa/Kami`，应用标识 `dev.umupa.kami`，构建产物 `Kami.app`，配置与日志目录 `Kami`，Operator 改动块 `kami-operator`，开发签名身份 `Kami Dev`。

**理由**：Kami 是日语里的「纸」，呼应翻译、润色、问答和随手记录这些处理文字的用途；一个名字到处一致，不必解释两个名字的关系。

**放弃**：另加中文名「墨」。

## D18 笔记是临时记录的草稿纸（2026-10-19）

**决定**：笔记是面板的一种特殊状态，在模式条最后一项，只能用 Tab 切入，没有专用的全局快捷键。正文是 Markdown，只着色、不改字。可以有多张，每张一个 `.md` 文件，默认在 `~/Library/Application Support/Kami/notes/`，`notesDir` 可改。删除进废纸篓。切换、搜索、新建都在挂在「全部笔记」按钮上方的弹出层里完成，选中时背后的编辑区以原高度只读预览那张，⏎ 才切换，搜不到时 ⏎ 直接用搜索词新建；⌘P 打开和关闭列表（同 Raycast Notes），⌘N 新建、⌘[ / ⌘] 前后切换；固定面板因此用 ⌘⇧P。

**理由**：临时记录要的是打开快、写下什么就是什么，粘贴链接被自动改写成 Markdown 之类的转换会打扰记录，所以只着色。放在面板里，风格与操作和其他模式一致；面板记住上次的模式，停在笔记时 ⌥空格直接回到笔记，不需要再占一个全局快捷键。一个文件一张笔记，可以放进同步目录，也能用别的编辑器打开。弹出层的卡片用来定位，背后的预览用来确认；预览沿用编辑区原来的高度，面板不随候选长短伸缩。

**放弃**：把面板结果存成笔记、对笔记做 AI 改写；独立的笔记窗口；纯文本与 Markdown 两种编辑模式并存；常驻的笔记侧栏（占宽度）；列表替换编辑区（看不到当前笔记）；列表与全文预览上下堆叠（窗口随预览长短跳动）；专用快捷键 ⌥N（占用输入 ñ 的死键）。

## D19 截图：冻结整屏、纸雾框选、固定翻译（2026-10-21）

**决定**：截图先冻结鼠标所在整块屏幕（按显示器 ID、原生像素、best 质量），在冻结画面上框选：屏保层级、真正无边框的非激活面板，纸雾、圆角选区与提示胶囊有独立于主面板的视觉 token（`internal/design/capture.go`）。松手后本机识别、恢复段落（D11）、固定翻译；采集、框选和识别期间其他入口等待。细节见需求 F2.4。

**理由**：冻结画面让框选不受屏幕变化影响，也让框选层能按画面亮度选择纸雾；截图是一条完整的操作链，任何一步出错都要回到原来的状态，所以和其他入口互斥。

**代价**：截图层多一套视觉 token；真实桌面的采集与权限只能手动验收，自动测试只用离屏生成的图片。

## D20 自定义主题写在 config.json 里（2026-10-22）

**决定**：自定义主题是 `config.json` 的 `themes` 数组，每项为 `id`、`name`、`base`（内置主题）与 `colors`（只写改动的颜色）。颜色用面板角色名，不用 Omarchy 的原始字段名。派生色（border、muted、faint、accentText、edge、operatorFill）未显式给出时随来源重算。`base` 只能是内置主题。对比度不达标只提醒，不拒绝。

**理由**：放在 `config.json` 里，Operator 的改动、校验、⌘Z 撤销、热加载和 `/theme` 预览都直接复用。用数组是因为改动路径不支持带连字符的键，`themes[N]`（N 为长度）即追加。角色名直接对应面板上的位置，用户和模型都不必知道「代码用 green」这类映射。有人确实想要低对比度，所以只提醒。

**放弃**：单独的主题文件目录（Operator 写不到，要另加监听）；覆盖内置主题（改坏后无从参照）；主题继承另一个自定义主题。

## D21 首次使用就是 Kami 的一段回复（2026-10-22）

**决定**：还没有模型时，启动即显示面板，结果区是 Kami 自己写的一段回复：一句说明加上配置提示词的代码块，像模型回复一样流式出字，用同样的排版、底栏和复制按钮；⏎、⌘C 都复制提示词。热加载读到模型后，Kami 接着回复「已连接」与授权步骤。配置类失败的说明行即「⌘C 复制提示词」。输入监控不在首次启动时请求，模型配好之后再请求。

**理由**：Kami 是一个对话式的工具，用户以后每天看到的就是这块结果区；引导也用它说话，才和整个应用是同一种东西。没有模型时唯一的下一步是把提示词交给 Coding Agent，所以回复里就是提示词本身，用户看得到要交出去的内容。

**放弃**：步骤条、卡片、权限表格这些专门的引导组件（与面板风格不搭）；多页向导窗口；启动时自动复制提示词（会覆盖用户的剪贴板）；在应用里填写 endpoint 与 Key 的表单（同 D13）；配置完成后自动弹出面板（打断用户在终端里的输入）。

## D22 只有一个模型（2026-10-22）

**决定**：`config.json` 只有一个 `model`，所有模式、追问与 Operator 都用它；没有 `models` 列表、`defaultModel` 和模式的 `model` 字段，`check` 不带模型名。旧的 `models` 写法按配置错误处理，不做兼容。

**理由**：翻译、润色、问答对模型的要求差别不大，「快速」「强」两套配置让第一次配置多一倍的选择，也让模式、提示词和检查都多一层「用哪个」。一个模型让配置提示词、首次使用和排错都只围绕一件事。想换模型，就让 Coding Agent 改这一处。

**放弃**：多个命名模型与按模式指定模型；对话中切换模型。

## D23 模型错误不阻断本地设置（2026-10-23）

**决定**：主题、字号、背景、快捷键等非模型设置独立于模型字段校验。模型字段不合法或仍是旧写法时，有效设置照常加载、保存并在重启后恢复；保留模型原始内容和错误提示，运行中沿用上次有效模型。`check` 仍严格校验整份文件。

**理由**：调整界面或快捷键不依赖模型可用，模型配置错误不能让本地设置失效。只放宽保存而不调整热加载会在重载或重启后丢失效果，两条路径必须使用相同边界。

**放弃**：只做内存预览；保存其他设置时自动迁移、清除或重编码模型字段。

## D24 只有一份配置提示词（2026-10-23）

**决定**：交给 Coding Agent 的配置提示词只有一份，不随配置状态变化。Agent 自己运行 `Kami check` 判断现在是没有模型、配置不合法、缺 Key、请求失败还是已经可用，按提示词里的对照表处理。从头配置是问答式向导：一次一个问题、给编号选项；手上只有订阅、没有 API Key 时，经 [magpie](https://github.com/yetone/magpie) 网关使用。配置类失败复制的也是这一份，不附失败详情。

**理由**：`check` 已经能区分每种状态，由 Kami 在复制那一刻替 Agent 判断，只会多出几套任务文案和一份会过期的快照（用户复制后又改了配置）。能把提示词交给 Coding Agent 的用户，手上多半就有一个订阅或 Key，magpie 能把它变成本机接口，所以「没有 Key」不必是死路。

**放弃**：按状态给出不同任务的提示词；提示词里的当前模型摘要；把失败的状态码与服务回复附进提示词（`check --verbose` 能重现；偶发失败重现不了时，Agent 如实说现在可用）。

## D25 菜单栏显示模型与连接状态（2026-10-23）

**决定**：菜单顶部常驻一行状态：SF Symbol 加当前模型名，颜色表示能不能用（绿色正常、橙色多半会自己恢复、红色需要处理）。模型配好或改动时（含每次启动）发一次与 `Kami check` 相同的最小请求；之后以用户每次请求的结果为准。

**理由**：Kami 平时只在菜单栏里，用户要在打开面板之前就知道它是否正常工作、用的是哪个模型。只看配置文件合法与否说明不了 Key 是否有效、服务是否可达；只看用户的请求结果，又要等到第一次失败才知道。

**代价**：每次启动和每次改模型多一次很小的请求（一个词的翻译），计入用户的额度。

**放弃**：定时检查（耗额度、耗电，且请求结果已经足够新）；把服务地址写进状态行（放在悬停提示里）。

## D26 Dock 可选显示，菜单栏保留（2026-10-23）

**决定**：`showInDock` 默认关闭，菜单栏提供「显示 Dock 图标／隐藏 Dock 图标」动作项，使用原生 `dock.rectangle` 图标，不用复选标记。设置立即保存并热加载，模型配置错误不阻断；开启后点击 Dock 图标唤起面板，关闭只隐藏 Dock 图标。菜单栏始终保留入口，图标单独绘制，不跟随 Dock 图稿。

**理由**：Dock 为习惯点击图标的用户提供入口，菜单栏保留快捷操作。启动先保持 accessory，ready 后再应用设置，避免框架按普通应用启动时抢焦点；切换显示本身不触发面板。

## D27 自更新：MyGo Updater、自签名、确认后才下载（2026-10-23）

**决定**：仓库公开，版本发布在 GitHub Releases；`scripts/release.sh` 在本机构建、用「Kami Dev」签名并上传，更新清单用钥匙串里的 ed25519 私钥签名。下载、校验、增量更新与替换都交给 MyGo Updater。打开面板时提示，确认「安装并重启」后才下载，面板开着就在完成后重启，离开面板则不自动重启。

**理由**：MyGo 已经提供签名清单、增量包和原子替换，不必自己实现。自签名不花钱，而且更新由 Kami 自己下载，不经过 Gatekeeper；只要每个版本都用同一个身份签名，指定要求不变，系统权限在更新后保留——所以只在本机发布，证书不进 CI。替换后的应用包与运行中的进程不再一致，macOS 会把它当作未授权（辅助功能检查失败），所以不在后台预先下载替换，而是等用户确认、紧接着重启。

**代价**：别人第一次安装要右键「打开」或在系统设置里「仍要打开」。以后换成 Developer ID 时指定要求会变，已安装的用户要重新授权一次。发布私钥丢失后，已安装的 Kami 再也收不到更新，要另外备份。

**放弃**：自己实现下载与替换；后台自动下载、退出时安装（替换后到重启前权限失效）；Developer ID 签名与公证（需要付费账号）。
