# 决策记录

每条记录写清楚决定、理由和放弃的方案。决定被推翻时，在原条目里写明新决定和日期，不另起重复条目。

## D1 重写，不 fork 辞达（2026-10-18）

**决定**：新建仓库，用 Go 重写；辞达只作为需求和设计的参考，不复制代码。

**理由**：
- 新场景碰到辞达的设计前提：它的提示词合约把输入一律当作材料，不当作指令，与问答、追问、提示词梳理冲突；结果栏是专为纯文本译文写的 TextKit 流式管线（`ResultTextView.swift` 约 1,300 行），加 Markdown 等于重写核心。
- 上游迭代很快（10 天 218 个提交），改动集中在 `AppModel`、`PanelView`，fork 后几乎每次同步都要解决冲突。
- 想换技术栈（Go + MyGo），fork 就只能写 Swift。

**放弃**：fork 后长期跟随上游；向上游提 Markdown 渲染。

**注意**：辞达是 Apache-2.0。参考它的规范和思路不受限制；如果移植具体代码，需要保留它的版权与许可声明。

## D2 用 MyGo 原生 UI，不用 SwiftUI，也不用 WebView（2026-10-18）

**决定**：界面用 MyGo 的 `ui` 包（Go 写、GPU 自绘、Core Text 排字），不用它的 WebView 模式。

**理由**：
- `ui/markdown` 自带为 LLM 流式回复设计的 GFM 渲染（增量解析、半截语法、匀速出字、淡入），正好是辞达缺的部分。
- 原生 UI 窗口打开即有内容、内存小，满足面板「按下即出现」。
- MyGo 已覆盖面板窗口、全局快捷键、菜单栏、透明窗口、文件监听和打包签名。

**代价**：MyGo 很新；输入法在自绘输入框上的表现要实测（见 tech-stack.md §九）。

**放弃**：SwiftUI + AppKit（成熟，但与想尝试 Go 的初衷不符）；MyGo WebView 模式（Markdown 生态更全，但唤起慢、内存大）。

## D3 系统 API 用 purego 直连，不用 cgo（2026-10-18）

**决定**：辅助功能、CGEvent（含事件监听）、NSPasteboard、Vision、ScreenCaptureKit 都通过 purego / purego/objc 调用，封装在 `internal/macos`。

**理由**：保持「纯 Go、无 cgo」，构建只要 Go；MyGo 自己就是这样调系统的。

**退路**：Objective-C block 或回调太难处理时，用 MyGo 的 helper executable 附带一个小的 Swift 工具，通过标准输入输出通信。

## D4 不保存会话（2026-10-18）

**决定**：会话、原文、结果只在内存里，退出即消失；日志不含文字。

**理由**：沿用辞达的隐私承诺；用户确认不需要保存提示词和历史，AI Chat 也不保存（2026-10-18 重新确认）。

**注意**：二期的笔记是用户主动保存的内容，不受这条约束，存储方式届时另定。

## D5 模式就是提示词预设（2026-10-18）

**决定**：模式 = 名字 × 提示词 × 输入语义 × 输出格式 × 默认模型（architecture.md §三）。所有模式走同一条管线，没有按模式分支的代码；内置翻译、改进、整理、提示词梳理、问答五个预设。

**理由**：翻译、改进、整理的差别只在提示词；场景再多也只是多一段提示词。

**放弃**（2026-10-18）：早先的设计还有语言规则、预处理、结果去处三个维度和「Agent 转译」模式。Agent 转译的边界说不清；预处理见 D11；结果去处只服务于原处改进，见 D10。

## D6 每个结果都可以追问（2026-10-18）

**决定**：多轮对话不是单独的窗口，而是任何结果之后的延伸；问答模式以对话开始。Material 模式的合约规定：第一条用户消息是材料，之后的用户消息是追问指令。

**理由**：多数时候用户要的是「把这段变成那样」，对话是对结果的调整；同时保住防注入。

## D7 开发期快捷键用 ⌃⌥，替换完成后改回 ⌥（2026-10-18）

**决定**：开发期 ⌃⌥A / ⌃⌥S，M4 改回 ⌥A / ⌥S。双击 ⌥ 辞达没有占用，一直使用。

**理由**：macOS 会把同一个热键同时发给所有注册了它的应用；过渡期两个应用并存。

## D8 自签名证书保证授权不丢（2026-10-18）

**决定**：自用阶段用本机自签名的代码签名证书。

**理由**：辅助功能和屏幕录制的授权绑定签名身份；临时签名每次构建都会变，授权随之失效。目前没有 Developer ID。

## D9 不依赖大模型 SDK（2026-10-18）

**决定**：`net/http` + 自写 SSE 解析器支持三种格式。

**理由**：只用到流式补全一个接口；三家 SDK 的依赖和行为差异不值得；与辞达的配置字段保持一致。

## D10 定位个人工具箱，只留三个入口（2026-10-18）

**决定**：一期是「辞达的翻译 + Raycast 的 AI Chat」，二期加笔记。入口只有双击 ⌥（打开面板）、⌥A（带入选区）、⌥S（截图）。不做原处改进（⌥F）和原处翻译（⌥D / ⌥⇧D），也不做听写。

**理由**：原处翻译是辞达里最大、最依赖辅助功能细节的子系统；原处改进要写回选区并核对原文没变。两者都不是我的高频用法，润色在面板里完成再复制即可。只给自己用，不为公开发布做取舍。

**放弃**：完整替代辞达的全部入口。

## D11 不做本机预处理（2026-10-18）

**决定**：终端输出清洗、截图识别的拼行、原文语言判断都不在本机做，交给模型，由提示词说明。截图识别出的行原样按行带进面板。

**理由**：输入来源枚举不完（各种终端、Agent 的标记符、排版），规则写不完也难维护；模型本来就能处理。

**代价**：多花一点 token；翻译方向偶尔需要追问纠正。

## D12 配置文件就是 agent 接口（2026-10-18）

**决定**：全部设置在带 JSON Schema 的 `config.json` 里，API Key 也在里面（每个模型的 `apiKey`），应用热加载；命令行只有 `check`；「复制配置提示词」交给 agent。（2026-10-18 修订：Key 原先存在登录钥匙串、经 `key set --stdin` 写入，见下。）

**理由**：沿用辞达「让 AI 助手配置」的思路（辞达 configuration.md §一），但更简单：agent 本来就会读写文件，不需要 `config set/show/schema` 这一套命令。Key 不能写进文件，检查需要真的发请求，所以留这两个命令。

**Key 为什么不放钥匙串**：钥匙串条目的分区列表在没有 Team ID 时记录的是二进制的 cdhash，自签名应用每重新构建一次都要重新授权；而且多一个 `key` 子命令。放进配置文件最简单，agent 一次就能配好。

**代价**：Key 以明文存在 `config.json`（权限 0600）；agent 读写这个文件时，Key 会进入它的上下文。配置提示词要求 agent 不复述 Key。备份工具会备份这个文件。早期存在钥匙串里的 Key，应用启动时自动搬进 `config.json` 并删除钥匙串条目。

**放弃**：辞达式完整命令行；MCP 服务（要常驻本地服务，超出需要）；登录钥匙串（自签名下频繁授权）；单独的 keys.json（多一个文件和一条规则，用户选择了更简单的做法）。

## D13 没有设置窗口，只有 Operator（2026-10-18）

**决定**：去掉设置窗口和菜单栏里的设置项。查看和修改设置的唯一入口是面板里的 `/operator`：用一句话问或改，由默认模型理解，应用校验后直接写入 `config.json`，可撤销。模型服务交给 Coding Agent。参考 monocode 的 `/operator`：命令变色、模式药丸、发送时的星星。

**理由**：设置窗口是传统软件的形态；这个应用的一切都在一个对话框里发生，设置也应该是对话。配好模型之后，应用能用这个模型配置自己，不用再去找 Coding Agent。

**放弃**：设置窗口（已实现后删除）；在对话流里插入卡片、按钮这类新组件（不够原生）；改动先确认再生效（多一步，撤销已足够）；在 Operator 里输入 API Key（还需要 endpoint 等，交给 Agent 更简单）。
